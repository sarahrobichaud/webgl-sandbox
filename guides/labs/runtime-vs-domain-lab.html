01 The word is overloaded

"Runtime" gets used for three unrelated things, which is exactly why it feels slippery:

  • The platform runtime — the JS engine / browser that executes your code. Not your concern here.
  • "At runtime" — an adverb meaning "while the program is running," as opposed to compile time.
  • Your Runtime class — a thing you named. This is the one that needs a crisp definition.
This lab is only about the third one. When we say runtime below, we mean the host that drives your game each frame — not the browser, not the adverb.

02 Two meanings, one instinct

Split every part of your engine into two buckets. Almost everything falls cleanly into one.

RUNTIME · the machinery that runs the game

Exists to make things happen over time and on screen. It is plumbing, not content.

  • the frame loop / requestAnimationFrame
  • the renderer + canvas
  • input devices
  • the scheduler (who ticks, how often)
  • scene management (what's drawn)

DOMAIN · the game itself

The stuff a save file is made of. It has meaning even with no window open.

  • the Session (the loaded game)
  • Simulations (airports)
  • money, reputation, routes
  • layouts, facilities, queues
  • rules and actions
The instinct in one line: if you deleted the window and the keyboard, the domain is what you'd still want to keep simulating and save to disk. The runtime is everything you'd have to rebuild to show it again.

04 Headless: run with no renderer

Here's the payoff for your game. If the domain is truly separate, a Simulation can tick with no renderer attached at all — which is exactly what a background airport is. Detach the screen below and watch the game keep running.

Runtime loop vs domain state
The trap: if entity data, money, or layout lived in the renderer or the Scene, "detached" would mean "dead." Detaching only stops the drawing because the numbers live in the domain.

05 Who owns what

Two jobs people cram into one "runtime" — keep them apart:

JobOwnerWhy
Own the set of simulations (create, load, save, dispose) Session It's the save. Airports exist because the player owns them.
Decide who ticks & how hard (foreground / background / dormant) Runtime scheduler It owns the frame loop and knows what's focused.
Advance one simulation (queues, money, flows) Simulation Pure game rules; no renderer, no input.
Decide what's on screen (active view + overlays) SceneManager Presentation only; reads domain, sends actions.
Foreground vs background is a policy, not a subclass. Same Simulation class — the scheduler just calls update() more or less often with a bigger or smaller game-step.

06 Mapping onto your code

Your stubs already sketch this shape. Here's the honest reading of each:

FileBucketShould hold
runtime/runtime.ts runtime Loop, renderer wiring, scheduler; coordinates Session + SceneManager. No game state of its own.
runtime/session/session.ts domain Map<LocaleId, Simulation>, money, reputation, routes, clock. This is the save.
runtime/simulation/simulation.ts domain One airport's state + update(step). Runnable with no renderer.
runtime/scene/scene.ts runtime Projection of a Simulation for display; render instances, camera, selection. Disposable.
core/instance.ts runtime Today it owns loop + renderer + world + input all at once — this is the god-object to split.
Current smell: instance.ts holds #world, #renderer, #camera, input, and the loop together. That fuses runtime and domain — which is why "where does this live?" keeps being ambiguous. Splitting it is the whole point of the new runtime/ folder.

07 A concrete default for Aero

The split to commit to

Runtime = loop + renderer + input + scheduler + scene management. Owns no game state.

Session = the loaded game. Owns the simulations and everything a save contains.

Simulation = one airport, headless. Ticks from a game-step; never touches the renderer.

Scene = a disposable projection of a Simulation for the player to look at and command.

Keep repeating the test. Looking at anything and unsure where it lives? Ask: "If I close this screen, must it still exist for the airport to keep making money?" Yes → domain (Session/Simulation). No → runtime/Scene.

Two tests worth designing against, because they force the boundary to stay honest:

  • Can you close a Scene and reopen it with nothing lost but camera and animation phase?
  • Can two Scenes observe one Simulation at once (map marker + detailed view)? If yes, "Scene owns the data" is impossible — good.
