Frame Bridge Lab

You’ve separated engine, game, and fidelity. This lab answers: what actually happens on one frame so those layers stay honest — especially when the player is on the map, in a site, or “paused” in a menu.

flow: input → intent → tick → draw rule: host drives, game decides, sim writes, view reads no code: pipeline thinking

01 The four beats of a frame

Ignore class names. Every healthy interactive loop rhymes with this:

1 · Host (engine)
Begin frame · sample devices · compute dt
Machinery. No idea what an airport is.
2 · Game intent
Map raw input → commands that mean something · respect mode (map / site / menu)
“Build runway”, “sign contract”, “zoom to map” live here — not in the renderer.
3 · Advance truth
If allowed: step full site and/or abstract businesses · apply commands
Numbers move. Empire + sim write; host does not invent money.
4 · Present
Scene reads current state · draw map or site · overlays
Projection only. Closing the view must not erase the playthrough.
Bridge, don’t blend. The host calls the game; the game calls the sim; the view reads the result. If the draw step starts mutating empire cash, the layers have collapsed.

05 Close the course

Three takeaways

1. Engine = reusable mechanisms. Game = empire meaning. Shell = accounts & documents.

2. One focused full site; background businesses stay abstract — same identity, different fidelity.

3. Each frame: host drives → game interprets → sim writes → view reads.

When a new feature idea appears, run it through those three. If it fails a test, you’ve found a layering bug early — cheap while the design is still soft.
