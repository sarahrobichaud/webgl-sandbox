Input Manager Lab

You’re an experienced app developer. Games need a different input habit: systems query a stable per-frame snapshot, they don’t subscribe to DOM events. This lab gets you from your stub InputManager to a keyboard manager wired through LogicContext — enough to move a camera or entity with WASD.

01 Events vs frame queries

In a React app, you often react to a keydown: open a modal, submit a form. In a game, input is sampled every tick alongside physics and AI.

App / UI habit

Event → handler → side effect. Order is “whenever the browser fires.”

Game habit

Event → update internal state → systems ask “is Jump down this frame?” during #update.

Why the indirection? Your game loop already owns time (deltaTime in Game.#update). Input must speak that same language, or movement speed, jump-once, and “key stuck after alt-tab” become chaos.

Notice: repeats, no notion of “this frame,” no game code involved.

02 Three questions systems ask

Almost every keyboard feature collapses to these three:

Query Means Use for
isDown(code) Held right now Continuous move, camera pan, charge
wasPressed(code) Went down this frame Jump once, open menu, fire once
wasReleased(code) Went up this frame Release charge, end drag
If you only store “isDown,” every system that wants a one-shot action invents its own previous-frame bookkeeping — or worse, fires every tick while the key is held.

Your current stub already has the continuous case: 

export interface InputManager {
  isKeyDown(key: string): boolean;
}

We’ll extend it with edge queries and a beginFrame() that the game loop calls once per tick.

Mental model: listeners only maintain “which keys are held.” Once per frame you diff against last frame’s held set to derive pressed/released. That way keys that arrived between RAF ticks still show up as edges.

04 Design the contract (~8 min)

Keep the interface in the engine, implementation free to change later (browser keyboard → +mouse → +gamepad). Prefer event.code ("KeyW") over event.key ("w" / "W" / layout-dependent). 

// src/engine/input/input-manager.ts
export interface InputManager {
  // continuous
  isDown(code: string): boolean;

  // edges — true for exactly one frame after beginFrame()
  wasPressed(code: string): boolean;
  wasReleased(code: string): boolean;

  // call once at the start of each logic tick (before systems)
  beginFrame(): void;

  // lifecycle
  attach(target?: Window | HTMLElement): void;
  detach(): void;
}
Naming: rename isKeyDown → isDown now while it’s still a stub. Later you can add isDown("Jump") via an action map without systems caring about KeySpace vs gamepad South.

What stays out of the interface

  • Entity IDs, camera, world — those belong in systems
  • Keybinding UI / persistence — later layer on top
  • “Player jumped” — that’s gameplay, not input

05 Implement keyboard state (~15 min)

Create src/engine/input/browser-keyboard-input.ts (name is flexible). Core idea:

export class BrowserKeyboardInput implements InputManager {
  #down = new Set<string>();      // live, mutated by DOM events
  #prevDown = new Set<string>();  // snapshot from last beginFrame
  #pressed = new Set<string>();
  #released = new Set<string>();
  #target: Window | HTMLElement | null = null;

  beginFrame() {
    this.#pressed.clear();
    this.#released.clear();

    for (const code of this.#down) {
      if (!this.#prevDown.has(code)) this.#pressed.add(code);
    }
    for (const code of this.#prevDown) {
      if (!this.#down.has(code)) this.#released.add(code);
    }

    this.#prevDown = new Set(this.#down);
  }

  isDown(code: string) { return this.#down.has(code); }
  wasPressed(code: string) { return this.#pressed.has(code); }
  wasReleased(code: string) { return this.#released.has(code); }

  attach(target: Window | HTMLElement = window) {
    this.detach();
    this.#target = target;
    target.addEventListener("keydown", this.#onDown);
    target.addEventListener("keyup", this.#onUp);
    window.addEventListener("blur", this.#onBlur);
  }

  detach() { /* remove the same listeners; clear sets */ }

  #onDown = (e: KeyboardEvent) => {
    if (e.repeat) return; // OS key-repeat ≠ new physical press
    this.#down.add(e.code);
  };

  #onUp = (e: KeyboardEvent) => {
    this.#down.delete(e.code);
  };

  #onBlur = () => {
    this.#down.clear(); // next beginFrame will emit releases vs #prevDown
  };
}
Why diff, not “push into pressed on keydown”? DOM events arrive between frames. If you clear a pressed-set at the start of the tick, you can wipe a key that fired during the last idle interval. Diffing #down vs #prevDown inside beginFrame() is the boring, correct fix.

Frame timing diagram

06 Wire into Areo’s loop (~10 min)

Your LogicContext already carries deltaTime, world, and camera. Add input the same way — systems stay pure consumers. 

// components.ts
export interface LogicContext {
  deltaTime: number;
  world: GameWorld<string>;
  camera: Camera;
  input: InputManager;  // ← add
}
// game-manager.ts (sketch)
#input = new BrowserKeyboardInput();

constructor(config) {
  …
  this.#input.attach(window); // or the canvas
  this.#logicContext = {
    deltaTime: 0,
    camera: this.#camera,
    world: this.#world,
    input: this.#input,
  };
}

#update(deltaTime: number) {
  this.#input.beginFrame();
  this.#logicContext.deltaTime = deltaTime;
  for (const logic of this.#logicComponents) {
    logic.update(this.#logicContext);
  }
}
Attach target: window is simplest for a canvas game that always “owns” the page. Attaching to the canvas only works if the canvas can receive focus (tabindex) — fine later, skip for v1.

07 Use it from a system (~10 min)

Start with something you can see immediately: camera pan or entity move. Prefer reading axes from keys rather than nesting ifs for every direction. 

// camera-system.ts or movement-system.ts
update({ input, camera, deltaTime }: LogicContext) {
  const speed = 8; // world units / second — tune later
  let x = 0, z = 0;
  if (input.isDown("KeyW")) z -= 1;
  if (input.isDown("KeyS")) z += 1;
  if (input.isDown("KeyA")) x -= 1;
  if (input.isDown("KeyD")) x += 1;

  // optional: normalize diagonal so W+D isn’t √2 faster
  const len = Math.hypot(x, z);
  if (len > 0) { x /= len; z /= len; }

  const dt = deltaTime / 1000; // your loop passes ms
  const p = camera.position;
  camera.setPosition({ x: p.x + x * speed * dt, y: p.y, z: p.z + z * speed * dt });

  if (input.wasPressed("Space")) {
    // one-shot: e.g. cycle mesh, toggle debug, jump impulse
  }
}

08 Browser gotchas (~5 min)

  • Stuck keys after alt-tab: you often miss keyup. Clear all downs on window.blur / visibilitychange. Try the “Simulate tab blur” button in §03.
  • event.repeat: browsers fire repeated keydowns while held. Ignore them for wasPressed or you’ll get jump spam.
  • code vs key: use code for physical keys (KeyW stays top-left letter even on AZERTY). Use key only for text entry.
  • preventDefault: optional for Space/arrows so the page doesn’t scroll. Don’t blanket-prevent everything — you still want Cmd/Ctrl shortcuts in the browser while developing.
  • Don’t put listeners in systems. Two systems attaching keydown = double handling and tears at teardown.
Anti-pattern: window.addEventListener("keydown", …) inside MovementSystem.update. That re-subscribes every frame or couples lifecycle to a system that may be disabled.

09 Done checklist

You’re done with this lab when all of these are true:

  • InputManager interface has isDown, wasPressed, wasReleased, beginFrame, attach/detach
  • BrowserKeyboardInput (or equivalent) implements it with Sets + blur clear
  • LogicContext exposes input
  • Game.#update calls input.beginFrame() before systems
  • One system moves something visible with WASD using isDown
  • One system uses wasPressed for a one-shot (Space is fine)

Default for Areo (ship this, not more)

Keyboard-only manager, physical code strings, no action map yet. Action names ("Move", "Jump") are a 20-minute follow-up once movement feels good — don’t block the first playable loop on rebinding.

Stretch (after the hour)

  • Action map: bind("Jump", "Space") then wasPressed("Jump")
  • Mouse: follow Mouse Input Lab — position, dx/dy, wheel, buttons
  • Pointer lock: for FPS look — only once mouse deltas work
