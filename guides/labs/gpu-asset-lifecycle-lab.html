01 CPU description vs GPU residency

Game code thinks in asset keys and vertex arrays. The GPU thinks in buffers, VAOs, and programs. Crossing that boundary is an explicit upload — not a side effect of importing a module.

CPU / game world

  • AssetCatalog — keyed descriptions (type: "mesh" + data)
  • MESHES.cube — vertices / normals as JS arrays
  • Cheap to allocate, easy to serialize, invisible to the GPU

GPU / device world

  • WebGLBuffer holding Float32Array copies
  • WebGLVertexArrayObject recording attribute layout
  • Expensive to create; stays until you delete it (or lose the context)
Bridge object. Aero stamps GPU handles onto the mesh itself: r_vao, r_programId. Until r_vao is set, render() must refuse to draw — the mesh is described, not resident.

02 Five lifecycle stages

1 · Describe
Author mesh data + catalog entry (ASSETS.cube, MESHES.cube)
Product content. No GL calls. Safe to hot-reload as data.
2 · Register
registerMeshes([...]) → runtime init → loadAssets
Bootstrap chooses which descriptions become candidates for upload.
3 · Upload
AreoGL.loadGeometry: create VAO, bufferData(STATIC_DRAW), stamp r_vao
The only step that spends VRAM. Happens once per mesh×program today.
4 · Bind & draw
bindVertexArray(mesh.r_vao) → set uniforms → drawArrays
Per-frame. Must not re-upload. CPU arrays are only used for vertex count.
5 · Dispose
Delete buffers / VAO · clear r_vao · drop catalog refs if unloading a level
Aero does not do this yet. Leaking here is silent until you thrash context memory.
Static draw contract. STATIC_DRAW means “upload rarely, draw often.” If you mutate mesh.vertices after upload, the GPU buffer does not change — you’d need a re-upload or a dynamic buffer strategy.

03 How Aero wires it today

Call chain from boot (main.ts) into WebGL:

game
catalog / MESHES — ASSETS keys descriptions; MESHES.* holds the actual arrays
shell
main.ts — instance.registerMeshes([MESHES.plane, MESHES.cube, MESHES.pyramid])
system
AeroSystem.registerMeshes → SystemRuntime.init
renderer
SceneRenderer.loadAssets → WebGlRenderer.init
gl helper
AreoGL.loadGeometry(program, meshes) — VAO + attribute buffers per mesh
draw
WebGlRenderer.render — bind VAO, uniforms, drawArrays(..., vertices.length / 3)
Separation that already works: the game owns what exists (catalog.ts); the engine owns how it becomes drawable. Catalog keys are the stable handle gameplay should prefer — not raw WebGLBuffer ids.
Current seam: main.ts still passes MESHES.* directly instead of resolving through ASSETS. Same data path — the catalog is the intended product-facing API; wire-up is unfinished.

05 Why VAOs (and per-program upload)

A VAO remembers: which buffers feed which attribute locations, and how to interpret them (size 3 floats, stride 0, …). Binding a VAO restores that whole setup in one call.

  • Upload path: create VAO → bind it → create buffers → vertexAttribPointer → unbind.
  • Draw path: bind that VAO → draw. No re-describing attributes every frame.
  • Aero quirk: WebGlRenderer.init uploads meshes for basic and the grid mesh for grid separately — attribute locations can differ per program, so VAOs are not freely shared.
HandleMeaningWho sets it
r_id Stable string id for the mesh asset Mesh author / catalog
r_vao GPU residency proof — drawable handle AreoGL.loadGeometry
r_programId Which program this VAO was built against AreoGL.loadGeometry
vertices (CPU) Source data + draw vertex count (length / 3) Mesh author; kept after upload today
LoadedMesh = Required<Mesh>. The type system encodes the contract: draw code expects every render hint to be present. Passing a bare catalog description into render should be a type error, not a black screen.

07 Gaps & next moves

What Aero has vs what a fuller asset manager usually adds:

CapabilityTodayTypical next step
Describe AssetCatalog + MESHES Resolve catalog keys → mesh data in one place
Upload Eager list at boot via registerMeshes Lazy / reference-counted load by scene need
Track buffers VAO only; buffers not stored for delete Keep buffer handles on the mesh or in a GPU registry
Dispose None deleteBuffer / deleteVertexArray + clear r_vao
Context loss Unhandled Mark all assets unloaded; re-upload on restore

Design rule to keep

Gameplay code names assets by catalog key ("cube"). Only the renderer turns that into r_vao. Entities should store a mesh ref, never a raw GL handle — otherwise context loss and hot-reload become distributed outages.

Upload is a lifecycle event, not a frame cost. Draw binds; it does not bufferData.
