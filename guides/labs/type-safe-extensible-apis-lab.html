Type-Safe Extensible APIs

Engines fail at the boundary: either everything is string and unsafe, or generics explode and nobody wants to call your API. This lab compares patterns for systems that stay type-safe, ergonomic to write against, and easy for a game project to extend — using Aero-shaped examples (actions, scenes, commands).

01 The consumer problem

You ship an engine. Someone else (you, later, or a game folder) ships a project with its own action names, scene ids, overlays, and domain commands. The engine cannot hardcode "ZOOM_IN" or "buildMenu" — but if every API takes string, autocomplete dies and typos ship.

engine
Defines capabilities + constraints. Knows shapes, not game vocabulary.
game
Supplies vocabulary: action registry, scene factories, command ports.
types
Should flow from game → call sites, not force game to cast through any.
Ergonomics test: can a junior add PAUSE to the action map and get input.isActive("PAUSE") autocomplete + typo errors — without touching engine source? If yes, the extension model is working.

Too loose

isActive(action: string)

Flexible, but every misspelled action is a runtime bug. No refactor rename.

Too rigid

Engine enum of all actions forever

Safe for demos, hostile to real games. Forces PRs into the engine for content.

03 Six patterns, side by side


  
A · Registry + satisfies + keyof typeof

  

    You already use this for actions. Engine defines a wide registry shape;
    game fills a const object; types are inferred from the object, not listed twice.
  

  
// engine
export type ActionRegistry = Record<string, { key: Button }>;

// game
export const Action = {
  ZOOM_IN: { key: KeyboardButton.KeyE },
  ZOOM_OUT: { key: KeyboardButton.KeyQ },
} satisfies ActionRegistry;

export type ActionCodes = keyof typeof Action;
// "ZOOM_IN" | "ZOOM_OUT"

  

    Why it feels good: one source of truth. Add a key → types update.
    satisfies checks shape without widening values to string.
  


  
B · Generic capability surfaces

  

    Engine APIs take a type parameter defaulting to string, but game code
    instantiates with its union. Inference at construction is the ergonomic trick.
  

  
// engine
interface InputManager<Action extends string = string> {
  isActive(action: Action): boolean;
}

// preserve Action through the factory
function createInput<R extends ActionRegistry>(
  registry: R,
): InputManager<keyof R & string>;

  

    Trap: if createInput returns InputManager<string>,
    you threw away the consumer’s vocabulary. Always thread keyof R out.
  


  
C · Schema / phantom generic on Scene

  

    Scene carries a type parameter describing this project’s vocabulary
    (actions, storage kind, overlay names). The value may not store the schema —
    it’s a compile-time phantom.
  

  
// engine
interface SceneSchema {
  actions: string;
  overlays?: string;
}

interface Scene<S extends SceneSchema = SceneSchema> {
  id: SceneId;
  // input in view context becomes InputManager<S["actions"]>
}

// game
type DemoSchema = {
  actions: ActionCodes;
  overlays: "hud" | "build";
};

function createDemoScene(): Scene<DemoSchema>;

  

    Use when several APIs must share one vocabulary (input + overlays + commands).
    Skip when a single registry already flows types — don’t nest phantoms for sport.
  


  
D · Branded ids

  

    Prevents mixing SceneId with EntityId even though both are numbers.
    Extension-friendly: game can add more brands without engine changes.
  

  
type SceneId = number & { readonly __brand: "SceneId" };
type EntityId = number & { readonly __brand: "EntityId" };

function SceneId(value: number): SceneId {
  return value as SceneId;
}

// switchTo(entityId) → type error

  

    Cheap safety for opaque handles. Pair with factories (SceneId(1)) so call sites stay readable.
  


  
E · Ports (commands), not event soup

  

    For domain writes, give consumers a typed interface they implement or receive —
    better ergonomics than a stringly event bus for “please do X.”
  

  
// engine or shared contracts
interface DomainCommands {
  setSimSpeed(mult: number): void;
  placeBuilding(input: { kind: string; cell: Cell }): Result;
}

// game narrows / extends
interface AeroCommands extends DomainCommands {
  placeBuilding(input: { kind: "gate" | "shop"; cell: Cell }): Result;
  assignGate(flight: EntityId, gate: EntityId): Result;
}

// controller closes over AeroCommands at createDemoScene(deps)

  

    Controllers stay generic over Cmds extends DomainCommands if the engine ships
    reusable controller helpers; otherwise game controllers just take AeroCommands.
  


  
F · Module augmentation (use sparingly)

  

    Consumers patch an engine interface via declare module. Powerful for plugin ecosystems;
    surprising for a single-game engine.
  

  
// engine
export interface EngineActions {}

// game ambient
declare module "@aero/engine" {
  interface EngineActions {
    ZOOM_IN: void;
    PAUSE: void;
  }
}
// engine InputManager<keyof EngineActions>

  

    Harder to trace, fights “vocabulary lives in game const objects,” and couples to module paths.
    Prefer satisfies + generics unless you are designing third-party plugins.
  







  
04 Composition recipe for Aero

  

    You don’t pick one pattern forever. Stack a few that each solve a different boundary.
  


  

    
      
BoundaryPatternAero touchpoint

    
    
      

        Input vocabulary
        satisfies + keyof + generic InputManager
        game/actions.ts → InputManager<ActionCodes>
      

      

        Opaque handles
        branded ids
        SceneId, EntityId
      

      

        Scene assembly
        factory returns concrete Scene; optional schema phantom
        createDemoScene(deps)
      

      

        Domain writes
        typed command port
        controller deps, not event bus
      

      

        Named parts
        Map<K, V> with K from schema or const keys
        overlays/views maps
      

    
  


  
// Sketch: types flow from game registries into engine surfaces
const Action = { ... } satisfies ActionRegistry;
type ActionCodes = keyof typeof Action;

function createDemoScene(deps: {
  input: InputManager<ActionCodes>;
  commands: AeroCommands;
}): Scene {
  const views = new Map([["map", new DemoView()]]);
  const controllers = new Map([
    ["build", new BuildController(deps.commands)],
  ]);
  return {
    id: SceneId(1),
    views,
    overlays: new Map(),
    controllers,
    onEnter() { /* activate */ },
    onExit() {},
  };
}


  

    Ergonomic order: define vocabulary as values → derive types → pass into factories →
    engine only sees generics/interfaces. Avoid re-declaring the same union in three files.

06 Defaults to commit to


  

    
Aero’s default stack

    
1. Registries with satisfies + keyof typeof for vocabularies (actions, maybe overlay names).

    
2. Generics on engine surfaces that must mention that vocabulary (InputManager<Action>).

    
3. Branded ids for opaque handles.

    
4. Typed command ports for controller → domain.

    
5. Scene factories in the game layer; engine accepts finished Scene.

    
6. Schema phantoms only when multiple APIs must share one schema — not by default.

    
7. Module augmentation only if you later want third-party plugins.

  


  

    Design smell: if adding a new action requires editing engine enums,
    your extension model failed. If every call site writes as ActionCodes,
    inference failed at the factory boundary.

Game authors adding content weekly.
