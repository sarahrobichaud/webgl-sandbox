World Scale Lab

Your floor felt “too big” and the debug colors looked weird because camera, meshes, entity scales, and grid tiles weren’t speaking the same language. This lab helps you pick one unit system and see how every piece should use it — before you finish the grid shader.

01 What’s going wrong today

In your renderer right now, several numbers live in different mental units:

  • Ortho uses the canvas size in pixels (0 … width, height … 0).
  • Camera translates by (-400, -400) — also pixel-ish.
  • Cubes spawn at x = -400, 0, 400 and get scaled to 50.
  • Floor plane is a unit mesh [-0.5, 0.5], then you scale it for how many tiles across.
  • Grid will use tileSize in whatever those world numbers happen to be.
Nothing here is “broken.” It’s just inconsistent. When the floor is 1600 units wide and you color by x / 20, of course almost everything saturates to pink.

02 Four spaces

Every vertex walks through these. Grid math must use world.

1 · Local / model

Numbers in the mesh file. Your plane/cube use [-0.5, 0.5] (1 unit across at scale 1).

2 · World

After translate / rotate / scale. “Meters on the map.” Floor grid, entity positions, and tile size all live here.

3 · View / camera

World, but relative to the camera. You rarely invent numbers here by hand.

4 · Clip / screen

After projection. GPU rasterizes triangles. Do not do grid fract on this.

Follow one corner of the unit plane
// same order as your renderer: T * R * S * local
worldPos = translate * rotateX * scale * vec3(1, 1, 0);

03 Pick what 1 unit means

You don’t need real-world meters. You need a sentence you can repeat:

“In Areo, 1 world unit = one gameplay tile edge.”

or

“In Areo, 1 world unit = 1 screen pixel at default zoom.” ← what you accidentally have now

Choose a convention
Either works. Mixing them does not. The rest of this lab assumes you pick one and drive camera + meshes + tiles from it.

04 Unit mesh × scale = world size

Your plane vertices span 1 local unit (from −0.5 to +0.5). World size on that axis ≈ scale (after rotation, which axis that is).

How big is the floor?
Rule of thumb: if the floor is 200 units across and tileSize = 1, you get ~200 cells. If you can’t see the lines, either zoom in, raise tileSize, or shrink the floor — don’t randomly multiply scale by 5000.

05 Your axes: XZ ground, Y up

docs/grid-system.md already says ground is XZ, height Y. The stock plane mesh is on XY (facing +Z), so you rotate it rotateX = 90° to lay it flat. After that:

  • Local X → world X (still left/right on the ground)
  • Local Y → world Z (depth on the ground)
  • World Y ≈ constant (floor height)
Which axes feed the grid?
// grid fragment — after the plane is tipped flat
float fx = fract(v_worldPos.x / u_tileSize);
float fz = fract(v_worldPos.z / u_tileSize);  // not .y

06 Ortho camera = how much world fits

Your projection is roughly: 

ortho(0, canvasWidth, canvasHeight, 0, -depth, depth)

That means: at identity view, 1 world unit ≈ 1 CSS pixel on screen. A cube scaled to 50 is ~50px wide. A floor scaled to 800 covers most of a big monitor.

That’s a valid convention (“pixel world”). The pain starts when you treat those numbers as “meters” or “tiles” without deciding.

09 A concrete default for Areo

You can change this later. For learning the grid, pick something boring and write it down.

Recommended starter (keeps your pixel-ish ortho)

1 world unit = 1 pixel at default zoom (matches current ortho).

1 gameplay tile = 50 units (matches your cube scale of 50 — one tile ≈ one cube footprint).

Floor: e.g. 40×40 tiles → plane scale = 40 (unit plane is −0.5…0.5).

Grid shader: u_tileSize = 50.0, sample v_worldPos.x and .z.

Entity positions: place on tile centers, e.g. tile (i, j) → (i * 50, height, j * 50).

Alternative (cleaner long-term)

1 world unit = 1 tile. Cubes at scale ~1. Floor scale ~ half tile count. u_tileSize = 1.

Then change ortho to something like “show N tiles across,” not canvas pixels. Bigger refactor — do it when the pixel-world starts fighting gameplay.

Before coding more grid: write your choice into docs/grid-system.md (unit meaning + tile size in world units + axes). Then every new number has a home.
