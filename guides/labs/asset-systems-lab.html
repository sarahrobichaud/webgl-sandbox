01 Three layers of “an asset”

People say “load the cube” and mean three different things. Name them separately or your API will smuggle GPU objects into gameplay and break on context loss / hot reload / level unload.

1 · Catalog key

  • Stable id: "cube", "ui/atlas"
  • Product vocabulary
  • Safe on entities & save data

2 · CPU description

  • Decoded bytes / arrays
  • Float32Array, ImageBitmap
  • Invisible to the GPU

3 · GPU residency

  • WebGLBuffer, VAO, texture
  • Created by explicit upload
  • Dies with context or dispose
Mental model: a catalog maps keys → descriptions. A loader / cache turns descriptions into CPU data (and tracks “is this ready?”). A GPU registry turns CPU data into device objects and is the only place that calls createBuffer / texImage2D / delete*.

02 Catalogs & game call sites

Game code’s job is to declare what exists and point at it by key. It should not invent GL objects, and it should not care whether the mesh is resident yet — that’s the engine’s readiness contract.

What a catalog is

A typed map from key → description. Descriptions are serializable product content (paths, inline vertex lists, sampler flags). No WebGL* types in here. 

// game owns vocabulary
const ASSETS = {
  cube:  { type: "mesh",  src: "/meshes/cube.json" },
  atlas: { type: "tex",   src: "/img/atlas.png", wrap: "clamp" },
} as const;

type AssetKey = keyof typeof ASSETS;  // "cube" | "atlas"

What entities store

Prefer

mesh: AssetKey or branded MeshId

Survives reload, context loss, and “not uploaded yet.”

Avoid

vao: WebGLVertexArrayObject on the entity

Handle is disposable; entity is not. Coupling = distributed outage.

Game vs engine call sites
Readiness is an engine concern. Gameplay can ask assets.isReady("cube") or wait on await assets.ensure(["cube"]). Drawing code that finds a missing GPU handle should skip or assert — not silently create buffers mid-frame.

03 WebGL residency lifecycle

Crossing into the GPU is an explicit sequence. Nothing you import or fetch becomes drawable until you allocate device objects and fill them.

1 · Describe
Catalog entry: key + type + source / inline data
Authoring time. Zero GL. Cheap to hot-reload as data.
2 · Acquire (CPU)
fetch / decode → typed arrays or ImageBitmap
Still host memory. Useful for CPU collision, baking, or re-upload after context loss.
3 · Upload (GPU)
createBuffer / createTexture + bufferData / texImage2D (+ VAO setup)
Spends VRAM. Returns a handle the renderer stores in a registry keyed by asset id.
4 · Bind & draw
bindVertexArray / bindTexture → uniforms → draw*
Per-frame. Must not call bufferData for static content. Upload ≠ draw.
5 · Dispose / context loss
deleteBuffer / deleteTexture / deleteVertexArray, or treat all handles as dead
JS GC does not free GPU memory. Losing the context orphans every handle.
STATIC_DRAW contract. After upload, mutating the CPU array does nothing to the GPU copy. Either re-upload (bufferSubData / new bufferData) or use a dynamic strategy deliberately.
VAOs remember layout, not ownership of “the mesh.” A VAO records which buffers feed which attribute locations for a given program’s layout. Attribute locations can differ per shader program — so “one VAO forever for this mesh” is not always true. Store enough info to rebuild if the program changes.
WebGL callLifecycle roleWhen
createBuffer / createTexture / createVertexArray Allocate residency Load / ensure — never every frame
bufferData / texImage2D Fill residency Load; rare updates if dynamic
bind* + draw* Use residency Every frame that needs it
delete* Release residency Unload / refcount → 0
context lost / restored Invalidate all handles Browser / GPU reset — re-upload from CPU cache

06 Buffers vs textures (same idea)

Meshes and images look different in APIs, but the three-layer story is identical.

Mesh / geometryTexture / image
Catalog key + vertex layout / path key + path + wrap/filter hints
CPU Float32Array positions / normals / uvs ImageBitmap / HTMLImageElement / raw pixels
Upload createBuffer + bufferData (+ VAO) createTexture + texImage2D + params
Draw bindVertexArray → drawArrays/Elements activeTexture + bindTexture → sample in shader
Dispose deleteBuffer / deleteVertexArray deleteTexture
One registry, many kinds. A practical asset manager is often Map<AssetKey, GpuSlot> where the slot is a discriminated union ({ kind: "mesh", vao, buffers } | { kind: "tex", texture }). Game code still only sees keys and readiness — not the union guts.

08 Defaults to commit to

Design rules worth keeping

1. Gameplay stores keys, never raw WebGL* handles.

2. Catalog = descriptions only. Loader = CPU readiness. GPU registry = residency + dispose.

3. Upload is a lifecycle event; draw only binds. Mid-frame bufferData for static meshes is a smell.

4. Keep enough CPU (or reloadable) data to survive context loss — handles are ephemeral.

5. If you can’t delete it, don’t create it casually. Track buffer/texture/VAO ids for dispose.

minimal API
ensure(keys) · isReady(key) · getGpu(key) (engine-internal) · release(keys) / refcount
game uses
ensure + keys on entities. Never getGpu from sim code.
renderer uses
getGpu after readiness; bind; draw; never invent catalog keys.
