ECS Approaches in TypeScript

Entity–Component–System is a data layout + iteration style, not one library. This lab compares the shapes you’ll actually meet in TS game code — from “object bags” to sparse sets and archetypes — and when each one is worth the complexity.

goal: pick a world model on purpose axes: ergonomics · scale · type safety bias: start simple, earn SoA

01 What ECS actually is

Classic OOP packs behavior into class hierarchies (FlyingVehicle extends Vehicle). ECS splits three roles so composition stays cheap and systems stay focused:

Entity
An id (opaque handle). Not a class full of methods — a ticket to look up data.
Component
Data only — position, velocity, mesh ref, “is boarding.” Prefer plain objects / structs.
System
Behavior over a query — “all entities with Position + Velocity, integrate.”

Composition

Add/remove components instead of inventing subclasses for every combo.

Cache-friendly work

Systems iterate one kind of data tightly. Layout decides whether that pays off.

Clear ownership

Simulation rules live in systems; entities don’t grow god-objects.

Litmus: if your “entity” still has update(), render(), and a subclass tree, you have GameObjects with a component bag — useful, but not yet the ECS that engines market.

03 Six approaches, with tradeoffs


  
A · OOP hierarchy (baseline anti-pattern for “ECS”)

  

    Behavior and state live on classes. New combos mean new subclasses or mixins.
    Fine for tiny prototypes; hostile once planes, gates, and UI widgets share bits of behavior.
  

  
class Entity {
  update(_dt: number) {}
  render() {}
}

class Movable extends Entity {
  x = 0; y = 0; vx = 0; vy = 0;
  update(dt: number) {
    this.x += this.vx * dt;
    this.y += this.vy * dt;
  }
}

class Plane extends Movable { /* boarding? fuel? AI? */ }

  

    

      
Advantages

      
    
        
  • Familiar; IDE navigates methods easily
    • 
        
  • Zero infrastructure to start
    • 
        
  • Encapsulation feels natural for UI widgets
    • 
      

    

    

      
Disadvantages

      
    
        
  • Combination explosion (FlyingRenderableSelectable…)
    • 
        
  • Hard to share “just velocity” across kinds
    • 
        
  • Systems can’t iterate dense data cleanly
    • 
      

    

  


  
B · Entity bag (components on the entity)

  

    Entity is still an object, but behavior moves to systems that query “who has X.”
    Components are usually a Map or typed bag. This is the most common “ECS in TS” starter.
  

  
type EntityId = number;

interface Entity {
  id: EntityId;
  components: Map<string, unknown>;
}

function movementSystem(entities: Entity[], dt: number) {
  for (const e of entities) {
    const p = e.components.get("position") as Position | undefined;
    const v = e.components.get("velocity") as Velocity | undefined;
    if (!p || !v) continue;
    p.x += v.x * dt;
  }
}

  

    

      
Advantages

      
    
        
  • Composition without subclass trees
    • 
        
  • Easy mental model; debug by inspecting one entity
    • 
        
  • Fast to ship for hundreds of entities
    • 
      

    

    

      
Disadvantages

      
    
        
  • String keys + casts unless you invest in typing
    • 
        
  • Queries scan every entity (or maintain secondary indexes)
    • 
        
  • Pointer-chasing: bad cache locality at scale
    • 
      

    

  

  

    Type upgrade: prefer
    components: { position?: Position; velocity?: Velocity }
    or a generic Entity<{ position: Position; velocity: Velocity }>
    over Map<string, unknown>.
  


  
C · Sparse-set component stores

  

    Entity is only an id. Each component type owns a store: sparse map from id → dense slot,
    dense array of values. Systems iterate one store (or zip two) instead of scanning entities.
    Deep dive with a live playground:
    Sparse-Set Stores lab.
  

  
type EntityId = number;

class Store<T> {
  dense: T[] = [];
  entities: EntityId[] = [];
  sparse = new Map<EntityId, number>(); // id → dense index

  has(id: EntityId) { return this.sparse.has(id); }
  get(id: EntityId) {
    const i = this.sparse.get(id);
    return i === undefined ? undefined : this.dense[i];
  }
  set(id: EntityId, value: T) { /* upsert into dense */ }
}

const positions = new Store<Position>();
const velocities = new Store<Velocity>();

function movement(dt: number) {
  for (let i = 0; i < velocities.dense.length; i++) {
    const id = velocities.entities[i];
    const p = positions.get(id);
    if (!p) continue;
    p.x += velocities.dense[i].x * dt;
  }
}

  

    

      
Advantages

      
    
        
  • O(1) add/remove/has; dense iteration per type
    • 
        
  • Clear “world owns stores” boundary
    • 
        
  • Sweet spot for mid-size sims (airports, units)
    • 
      

    

    

      
Disadvantages

      
    
        
  • Multi-component queries need join logic
    • 
        
  • More boilerplate than entity bags
    • 
        
  • Still object references in JS (not true SoA)
    • 
      

    

  


  
D · Archetype / table ECS

  

    Entities with the same component set live in one table (archetype). Adding a component
    moves the entity to another table. Queries become “scan matching tables” — great locality when
    many entities share the same shape.
  

  
// Conceptual — libraries: flecs, bevy, Unity DOTS, bitECS archetypes
type Archetype = {
  signature: bigint;          // bitset of component ids
  entities: EntityId[];
  columns: Map<ComponentId, unknown[]>; // SoA columns
};

// Query Position+Velocity → iterate only archetypes whose signature matches
for (const table of world.tablesMatching(POS | VEL)) {
  const xs = table.columns.get(POS) as Position[];
  const vs = table.columns.get(VEL) as Velocity[];
  for (let i = 0; i < table.entities.length; i++) {
    xs[i].x += vs[i].x * dt;
  }
}

  

    

      
Advantages

      
    
        
  • Best iteration locality for homogeneous crowds
    • 
        
  • Queries compile to table lists
    • 
        
  • Structural changes are explicit (move row)
    • 
      

    

    

      
Disadvantages

      
    
        
  • Harder to implement correctly
    • 
        
  • Add/remove component can be expensive (row migrate)
    • 
        
  • Many unique combos → table fragmentation
    • 
      

    

  

  

    When fragmentation hurts: every entity has a unique tag combo → many tiny tables.
    Sparse sets (or fewer, coarser components) may win.
  


  
E · Typed-array / SoA ECS (bitECS-style)

  

    Components are columns of Float32Array / Uint8Array, not JS objects.
    Maximum throughput; weaker ergonomics and typing unless wrapped carefully.
  

  
const Position = { x: new Float32Array(MAX), y: new Float32Array(MAX) };
const Velocity = { x: new Float32Array(MAX), y: new Float32Array(MAX) };

// eid is an index into the columns
function movement(eids: Uint32Array, n: number, dt: number) {
  for (let i = 0; i < n; i++) {
    const e = eids[i];
    Position.x[e] += Velocity.x[e] * dt;
    Position.y[e] += Velocity.y[e] * dt;
  }
}

  

    

      
Advantages

      
    
        
  • True contiguous memory; GC pressure drops
    • 
        
  • Ideal for particles, boids, huge unit counts
    • 
        
  • Maps cleanly to WASM / workers later
    • 
      

    

    

      
Disadvantages

      
    
        
  • Awkward for stringy / nested game data
    • 
        
  • TS types are thin wrappers or nonexistent
    • 
        
  • Debugging “object identity” disappears
    • 
      

    

  


  
F · Hybrid scene graph + ECS stores

  

    Presentation keeps a tree (parent transforms, UI, cameras). Simulation keeps flat stores.
    Controllers / systems write domain stores; render systems read them into the scene.
  

  
// Domain (flat)
world.positions.set(plane, { x, y, z });
world.boarding.set(plane, { gate, phase: "taxi" });

// Scene (tree) — presentation only
sceneNode.setLocalTransform(fromPosition(world.positions.get(plane)));

// Never put money / queues on the Three.js / custom scene node

  

    

      
Advantages

      
    
        
  • Matches how engines actually ship
    • 
        
  • Headless sim stays possible (see runtime vs domain lab)
    • 
        
  • UI/camera stay hierarchical where that helps
    • 
      

    

    

      
Disadvantages

      
    
        
  • Two representations to keep in sync
    • 
        
  • Easy to “leak” sim state into scene nodes
    • 
        
  • Needs discipline at the boundary
    • 
      

    

  







  
04 Why layout matters

  

    Same system, different memory shapes. Hot loops care about how many pointers you chase
    between “read velocity” and “write position.”
  


  

    

      
Layout sketch

      

        
        
        
      

    

    

    

  


  

    In JavaScript you rarely get C-like cache wins for free — objects are heap-allocated.
    Layout still matters for iteration cost, GC, and
    how hard joins are. Typed arrays are when you truly care about contiguous bytes.
  







  
05 Cheat sheet

  

    
      

        Approach
        Best when
        Avoid when
      

    
    
      

        OOP hierarchy
        Throwaway prototype, <20 kinds
        Many cross-cutting behaviors
      

      

        Entity bag
        Gameplay prototyping, <1–2k entities
        Hot loops over huge homogeneous sets
      

      

        Sparse-set stores
        Simulation worlds, frequent add/remove
        You need max SoA throughput
      

      

        Archetype tables
        Many entities, few stable shapes
        Wildly unique component combos
      

      

        Typed-array ECS
        Particles, flocking, huge unit counts
        Rich nested domain objects
      

      

        Hybrid scene + stores
        Real engines with cameras/UI trees
        You’re unwilling to police the boundary
      

    
  


  

    
      

        Concern
        Prefer
      

    
    
      

        Components as classes with methods
        Usually no — keep data dumb; put logic in systems
      

      

        Systems as classes
        Fine if they hold deps (scheduler, resources); update(world, dt) is enough
      

      

        Tags (empty components)
        Yes — Selected, Paused beat boolean soup on one mega-component
      

      

        Events / commands
        Side channel or command buffers — don’t overload components as mailboxes forever
      

      

        TypeScript typing
        Registry of component defs + typed get<C> / query helpers; avoid unknown casts

07 Defaults for Aero


  

    
Recommended progression

    

      1. Domain simulation: sparse-set stores (or a thin World wrapper around them)
      with branded EntityId and plain component interfaces.
    

    

      2. Presentation: hybrid — scene graph / renderer nodes project from stores;
      never own money, queues, or boarding state.
    

    

      3. Reach for archetypes or typed arrays only when a profiler says a hot system
      is entity-count bound (crowds, particles), not because “real ECS” blogs say so.
    

  


  

    API shape that ages well:
    world.query(Position, Velocity) returning an iterator of
    [EntityId, Position, Velocity] — implement with bags first, swap the World guts later
    without rewriting every system.
  


  
// Stable system surface — storage can change underneath
interface World {
  create(): EntityId;
  destroy(id: EntityId): void;
  add<C extends Component>(id: EntityId, ctor: ComponentDef<C>, value: C): void;
  get<C extends Component>(id: EntityId, ctor: ComponentDef<C>): C | undefined;
  query<Cs extends Component[]>(
    ...ctors: { [K in keyof Cs]: ComponentDef<Cs[K]> }
  ): Iterable<[EntityId, ...Cs]>;
}

function movementSystem(world: World, dt: number) {
  for (const [id, p, v] of world.query(Position, Velocity)) {
    p.x += v.x * dt;
    p.y += v.y * dt;
  }
}


  

    Pair this with the Runtime vs Domain and
    Type-Safe Extensible APIs labs:
    World lives in the domain; the runtime only schedules systems and projects to the scene.
