Input Architecture Lab

Input isn’t one class — it’s a pipeline of responsibilities. This lab maps the stack: device drivers → frame orchestration → engine contracts → game actions → binding maps. You’ll see where Areo sits today, and what each layer is (and isn’t) allowed to know.

01 The five-layer stack

Think bottom-up: hardware noise becomes gameplay intent. Click a layer to see what it owns.

Layer 1 · hardware / OS / browser
Device level

Raw events: keydown, mousemove, gamepad poll. Physical codes, not “Jump.”

Layer 2 · frame boundary
Orchestration

Once per tick: snapshot, edge-detect, clear deltas. Speaks “this frame.”

Layer 3 · reusable engine API
Engine level

Contracts + implementations. Systems query isDown / wasPressed.

Layer 4 · remappable names
Binding system

Maps action ids → device codes. Settings, presets, multi-device OR.

Layer 5 · your title
Game / project level

Systems react to actions: move camera, jump, open inventory. Never listen to DOM.

BrowserEvent → DeviceState → beginFrame() → FrameSnapshot → Bindings.resolve() → Action queries → Systems
Why so many layers? So you can swap a device (keyboard → gamepad), change a binding (Space → gamepad South), or rewrite a system — without rewriting the others.

02 Device level

A device adapter owns one hardware surface. Its job is narrow: translate platform events into a live state bag.

Owns

Listeners / polling, physical identifiers (KeyW, mouse button 0), held sets, position / axis buffers, blur / disconnect cleanup.

Must not own

Action names, gameplay decisions, entity IDs, “player jumped,” knowledge of other devices.

Device State it accumulates Platform source
Keyboard Which KeyCodes are held keydown / keyup
Mouse Buttons held, cursor xy, dx/dy, wheel mousedown, mousemove, wheel
Gamepad Buttons + axes (usually polled) navigator.getGamepads()
Touch Pointers / virtual sticks Pointer / touch events 
// Shape every digital device tends to share
interface withButtonInputs<Code extends string | number> {
  isDown(code: Code): boolean;
  wasPressed(code: Code): boolean;
  wasReleased(code: Code): boolean;
}
Areo today: BrowserKeyboardInputs and BrowserMouseInputs are device-level classes. They speak KeyCode / MouseButton, not "Jump".

Physical codes, not characters

Prefer event.code (KeyW) over event.key (w/W). Bindings stay stable across keyboard layouts; text entry is a separate concern.

03 Orchestration

The game loop is the conductor. Devices mutate state whenever the OS fires; systems must ask questions about this frame. Orchestration is the seam.

between frames
DOM / OS events mutate live device state
tick start
beginFrame() → diff → pressed / released / consume deltas
logic
systems query stable snapshot
draw
render (usually doesn’t re-read input)
// game-manager.ts — orchestration lives here, not in systems
#update(deltaTime: number) {
  this.#keyboardInputs.beginFrame();  // ← orchestration
  this.#logicContext.deltaTime = deltaTime;
  for (const logic of this.#logicComponents) {
    logic.update(this.#logicContext);  // ← consumers
  }
}

Orchestration does

Call beginFrame() on every device once, in a fixed order, before any system runs. Own attach/detach lifecycle with the game.

Orchestration doesn’t

Interpret WASD as movement. Know what “Jump” means. Subscribe to keydown inside a system’s update.

The classic bug: push into a pressed set on keydown, then clear it at the start of the next frame. Events that arrive while the tab is idle get wiped before systems see them. Diffing held vs previous-held inside beginFrame() fixes that.

Who calls beginFrame?

  • One place — the game loop (Areo: Game.#update)
  • If you later have keyboard + mouse + gamepad, either call each, or have a façade InputHub.beginFrame() that fans out
  • Never let two systems each call beginFrame — edges would vanish mid-tick

04 Engine level

Engine code is what you’d reuse in a different game. It defines contracts (interfaces) and platform implementations, then exposes them to systems via LogicContext.

Contracts

input-manager.contract.ts, key-codes.contract.ts — stable types, no DOM.

Implementations

browser-keyboard-inputs.ts, mouse, later gamepad — swappable.

Context

LogicContext.input (or .keyboard) — systems depend on the contract only.

// Engine boundary: reusable, game-agnostic
export interface InputManager {
  isDown(code: KeyCode): boolean;
  wasPressed(code: KeyCode): boolean;
  wasReleased(code: KeyCode): boolean;
  beginFrame(): void;
  attach(target?: Window | HTMLElement): void;
  detach(): void;
}
Engine vs game smell test: if the name only makes sense in your title ("OpenInventory", "CastFireball"), it doesn’t belong in the engine contract. Physical codes and generic queries do.

What “engine level” looks like as it grows

05 Game / project level

Game code is Areo-specific (or title-specific): systems, entities, rules. Systems should ask intent, not parse hardware — even if today that intent is still spelled KeyW until you add bindings.

Good (game)

CameraSystem pans when move-forward is active. MeshSwitchSystem cycles on a one-shot. Speed, who moves, and what happens live here.

Bad (leaks)

addEventListener inside update. Hard-coding layout-specific characters. Clearing key state from a system. 

// Today (device codes in a system — ok for v1)
if (input.isDown(KeyCode.KeyW)) position.x += speed;

// Target (action names — after bindings)
if (actions.isDown("MoveForward")) position.x += speed;
if (actions.wasPressed("Jump")) applyImpulse();
Progression, not perfection: shipping WASD via KeyCode in a system is fine. The architecture rule is: don’t let the system own listeners or frame edges. Bindings are the next peel of the onion.

Contexts of control

Games often need more than one “who is listening” mode — gameplay, UI menu, text chat, cutscene. That’s still game-level policy: an input context stack that enables/disables action sets. The engine supplies the raw/action queries; the game decides which set is active.

06 Binding system

Bindings sit between engine snapshots and game systems. They answer: “Which device codes currently mean Jump?”

engine
isDown(KeySpace) · isDown(GamepadSouth)
bindings
Jump → [Space, GamepadSouth]
game
wasPressed("Jump")

Core ideas

  • Action id — stable string or enum: "Jump", "MoveX"
  • Binding — one or more device sources OR’d together
  • Digital — buttons/keys → down / pressed / released
  • Analog — axes / sticks → float in [-1, 1] (optional composite from WASD)
  • Rebind — listen for next press, write into the map, persist
type ActionId = "MoveForward" | "MoveBack" | "Jump" | "Interact";

interface ActionMap {
  bind(action: ActionId, ...codes: KeyCode[]): void;
  isDown(action: ActionId): boolean;
  wasPressed(action: ActionId): boolean;
  wasReleased(action: ActionId): boolean;
}

// Resolve: action is down if ANY bound code is down
isDown(action) {
  return this.#map.get(action)!.some(code => keyboard.isDown(code));
}

Belongs in bindings

Default presets, user overrides, composite axes, “listen for rebind” UI helpers.

Still not bindings

Jump height, cooldown, which entity moves — those stay in systems / components.

Don’t merge layers early. An InputManager that both owns DOM listeners and action names becomes hard to test and hard to multi-device. Keep devices dumb; let a thin ActionMap translate.

08 Where Areo is today

Map the repo onto the stack so you know what to build next vs what to leave alone.

Layer Areo status Files

Orchestration Present Game.#update → beginFrame() then systems
Engine Contracts + context wired input-manager.contract.ts, LogicContext
Bindings Not yet —
Game Systems query device codes camera-system.ts, etc.

Recommended build order for Areo

1) Finish device managers (keyboard solid, mouse parity).
2) Keep orchestration in Game.#update — add mouse beginFrame beside keyboard.
3) Only then add a thin ActionMap and migrate systems off raw KeyCode.

Skipping ahead to rebinding UI before mouse/gamepad exist usually creates a façade that only wraps one device — rebuild later.

09 Ownership rules

When you’re unsure where a feature goes, use this cheat sheet.

Question Put it in…
“Did the physical W key go down?” Device (+ engine query API)
“When do we snapshot edges?” Orchestration (game loop)
“What’s the TypeScript shape systems depend on?” Engine contract
“Is Space or South the Jump button?” Bindings
“How high does Jump launch the player?” Game system / component
“Should menus eat gameplay input?” Game (input contexts / modes)
Anti-pattern: one god InputManager that attaches DOM listeners, stores action names, applies movement, and opens the pause menu. You’ll never unit-test half of it, and the next device breaks everything.

10 Checklist + next steps

You’re done with this lab when you can explain each layer in one sentence:

  • Device: accumulates raw hardware state (no gameplay names)
  • Orchestration: one beginFrame per tick before systems
  • Engine: contracts + platform impls exposed on LogicContext
  • Bindings: action ids → device codes (optional until rebinding matters)
  • Game: systems query intent and apply rules
